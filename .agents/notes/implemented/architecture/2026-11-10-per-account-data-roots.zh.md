# Agent Note: Per-account harness data roots

Status: implemented

[English](2026-11-10-per-account-data-roots.md) | 中文

## 问题

登录是产品进入工作区的唯一入口，而一台机器会服务多个账号：共用工位、一人双号，或在个人与工作身份之间切换的开发者。Harness 主目录是一个单一目录，保存会话、设置、待办、指令文件、技能、溢出输出与已存凭据，所有消费方都从这一个路径派生。于是同一台机器上的两个账号会互相读到对方的 Session 历史与配置，而本机 Host API 没有按账号鉴权，任何持有该机主目录的进程都能服务别人的数据。产品要求隔离：同一台机器上，一个登录账号的数据不能被另一个账号读到，同时升级后的机器要继续为原本拥有既成数据的用户工作。

## 决策

一个指针文件加一处解析器改动就承担了隔离，所有消费方都不必感知账号。`@deepseek-ai/dsh-home-paths` 先按既有优先级解析基础主目录（[单一 Harness 主目录解析器](2026-07-24-single-harness-home-resolver.zh.md)），再读取 `<base>/account.json` 并收窄：

```
no pointer, or activeUid === firstOwnerUid  >  <base>
any other activeUid                          >  <base>/accounts/<uid>
```

指针保存 `activeUid` 与 `firstOwnerUid`，其中 `firstOwnerUid` 只写一次、永不重指：在该机器上最先登录的账号拥有基础主目录里已有的数据，之后的每个账号都在 `accounts/` 下得到自己的根目录。`resolveDshHome()` 每次调用都读取指针而不做缓存，因为登录会在进程运行期间改写它；每个消费方仍然只在启动时解析一次，这正是根目录变化必须重启的原因。`dshBaseHome()` 返回未收窄的根目录，供真正拥有指针文件本身的代码使用；`accountDataRoot()` 与 `ownsHarnessHome()` 也是账号 provider 决定凭据交接到哪里时使用的同一组原语。

退出登录把 `activeUid` 置为 null 并保留 `firstOwnerUid`，因此归属关系随本人离开和回来都保持不变。写入指针时基础主目录按 `0700` 创建、文件按 `0600` 写入，先落到同目录的 `tmp-<pid>-<uuid>`，再 `rename` 就位。`readAccountPointer()` 只把「文件不存在」当作无指针：其他任何失败，或 id 不符合 `ACCOUNT_UID_PATTERN`，都会抛出，因为静默跳过损坏的指针会把首个账号的数据交给第二个账号。

账号 provider 在登录提交确认成功后最后写指针：先把授权写入目标根目录，再写指针，随后删除启动根目录中的副本，且只在写入确认成功后删除。目标写入未确认时指针保持不动，下次启动继续读取仍在原处的那份凭据。

由于每个进程在启动时就固定了自己的根目录，指针选中的根目录与运行中进程自身根目录不一致时，状态报告 `AccountView.restartRequired`，而不是悄悄按新根目录继续服务。桌面端拥有自己的 Host 进程，所以主进程每次运行只提示一次重启，被接受后重启应用并跳过退出确认；Web 只在登录界面给出手动重启提示，因为一个部署可能同时服务其他窗口与进行中的会话，自动重启会毁掉并不属于登录者本人的工作。

子进程隔离由环境继承而来，而不需要第二套解析：`dsh-subprocess` 在子进程环境白名单里重新声明已解析的 `DSH_HOME`，因此 agent 启动的嵌套命令落在同一账号根目录，而不会退回 `~/.dsh`。

## 考虑过的替代方案

**把账号 id 传给每个主目录消费方。** 会话、设置、技能、溢出、待办与凭据今天各自接收路径；把 uid 串到全部消费方意味着每个新增消费方都可能把隔离做错，一个过期调用方就会跨账号泄漏。在唯一解析器内部收窄，使正确的隔离成为唯一可获得的行为。

**每个账号一个顶层根目录（`~/.dsh-<uid>`）。** 它放弃了解析器拥有的单根目录规则，使 `$DSH_HOME` 因账号而异，让 `~/.dsh` 里的既有数据成为孤儿，还要重写所有点名 `~/.dsh` 的支持文档与指令路径。

**首次登录时把基础主目录迁进首个账号的根目录。** 布局更统一，但它在任何确认写入能够兜底之前复制或移动用户的全部历史，而升级后第二个登录的账号什么也继承不到。继承基础主目录对后续账号提供同样的隔离，且不需要批量搬移。

**Web 也自动重启 Host。** 桌面端重启不会伤及他人；Web 部署可能持有多个窗口和后台会话，由登录触发的进程重启会毁掉不属于登录者的工作。W1 只做提示。

**按进程缓存收窄后的根目录。** 缓存会在登录改写指针之后继续服务启动根目录，那正是 `restartRequired` 要报告的状态；每次调用读取指针让解析器保持诚实，代价只是每次启动多读一个小文件。

## 后果

- 改变根目录的登录只在下一个进程生效，因此产品为每次切号付出一次重启提示，并需要显式的 `restartRequired` 状态，以及一份绝不留下两份可读副本的凭据交接。
- 基础主目录是共享机制：指针与 `accounts/` 都在其中，所以指针损坏会让每次启动都停下来直到被修复，而账号 provider 是唯一的写入者。
- 指向账号根目录的 `$DSH_HOME` 原样解析，使嵌套进程与刻意的单账号启动无需第二个环境变量就能正常工作。
- 隔离是目录范围的，不做加密也不做访问控制：它阻止同机另一个账号经由 harness 读取，而不是阻止以同一系统用户身份直接点名该路径的进程。
- 模型 API key 与凭据遵循同一规则，因为它们就保存在主目录之下；没有另建 key 命名空间。
